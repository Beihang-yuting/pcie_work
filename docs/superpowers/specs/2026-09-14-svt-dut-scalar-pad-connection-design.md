# SVT DUT Scalar Pad Connection Design

## Goal

为 SVT RC + 真实 DUT EP 的 Serial 集成提供可复用的 scalar-pad 连接契约，
支持每组 16 条单 bit 差分 lane、x4/x8/x16 链路宽度，并在集成文档中说明
Passive Monitor 与 bit clock 的要求。

## Scope

- 支持两组 DUT pad：`pad0_phy_*` 和 `pad1_phy_*`，每组 lane 0 到 15。
- 每条 lane 的正端使用 `_p`，负端使用 `_m`。
- DUT 输入命名为 `padN_phy_rx<lane>_p/m`，DUT 输出命名为
  `padN_phy_tx<lane>_p/m`。
- 保持现有 `pcie_svt_serial_port_if` 和
  `PCIE_SVT_DECLARE_HDL_AGENT_X4/X8/X16` 不变。
- 复用已有 `pcie_svt_serial_port_if #(LANES=16)` 作为 pad 向量视图；新增的
  scalar binder 与连接宏直接定义在
  `svt_pcie_integration/rtl/pcie_svt_hdl_agent_macros.svh`，不额外引入
  adapter 源文件或新的 interface 类型。
- 不把 DUT PHY reference clock 混入 Serial data connector；reference clock
  由 DUT 顶层自行连接。

## Public interfaces

pad 向量复用已有 `pcie_svt_serial_port_if #(LANES=16)`，字段如下：

```systemverilog
interface pcie_svt_serial_port_if #(int LANES = 16);
  logic [LANES-1:0] rx_p; // SVT TX -> DUT RX positive
  logic [LANES-1:0] rx_n; // SVT TX -> DUT RX negative
  logic [LANES-1:0] tx_p; // DUT TX -> SVT RX positive
  logic [LANES-1:0] tx_n; // DUT TX -> SVT RX negative
endinterface
```

The public field names intentionally follow the DUT boundary.  They do not mean
that `svt_port.rx_*` is generated by the SVT receiver: in the existing adapter,
SVT `tx_datap/tx_datan` drive `svt_port.rx_p/rx_n`, while DUT `tx_p/tx_n` drive
`svt_port.tx_p/tx_n` and are forwarded to SVT `rx_datap/rx_datan`.

## Scalar pad binding

`PCIE_SVT_BIND_PAD16_SCALAR(pad_if, pad_prefix)` maps all 16 scalar lanes of one
DUT pad group to the `pcie_svt_serial_port_if #(16)` vector view.  For
`pad_prefix=pad0`, lane 0 expands to:

```systemverilog
assign pad0_phy_rx0_p = pad_if.rx_p[0];
assign pad0_phy_rx0_m = pad_if.rx_n[0];
assign pad_if.tx_p[0] = pad0_phy_tx0_p;
assign pad_if.tx_n[0] = pad0_phy_tx0_m;
```

The macro is directional and contains no clock, reset, `clkreq`, or `wake`
assignments.

## Width connectors

The data connector macros use an indexed part-select, so one implementation
supports all lane offsets without token arithmetic:

```systemverilog
`PCIE_SVT_CONNECT_DUT_SERDES_X4 (svt_port, pad_if, base_lane)
`PCIE_SVT_CONNECT_DUT_SERDES_X8 (svt_port, pad_if, base_lane)
`PCIE_SVT_CONNECT_DUT_SERDES_X16(svt_port, pad_if, base_lane)
```

Each connector expands to:

```systemverilog
assign pad_if.rx_p[base_lane +: WIDTH] = svt_port.rx_p;
assign pad_if.rx_n[base_lane +: WIDTH] = svt_port.rx_n;
assign svt_port.tx_p = pad_if.tx_p[base_lane +: WIDTH];
assign svt_port.tx_n = pad_if.tx_n[base_lane +: WIDTH];
```

The intended four-x8 topology is:

```systemverilog
`PCIE_SVT_CONNECT_DUT_SERDES_X8(svt_rc0_serial, pad0_if,  0)
`PCIE_SVT_CONNECT_DUT_SERDES_X8(svt_rc1_serial, pad0_if,  8)
`PCIE_SVT_CONNECT_DUT_SERDES_X8(svt_rc2_serial, pad1_if,  0)
`PCIE_SVT_CONNECT_DUT_SERDES_X8(svt_rc3_serial, pad1_if,  8)
```

An x16 connector occupies one complete pad group at `base_lane=0`.  A link that
spans pad0 and pad1 is deliberately outside this first contract and must use a
separate explicit cross-pad connector.

## Passive Monitor clocks

The SVT Serial Passive Monitor only observes serial symbols; it does not create
its own clock recovery.  When an upstream/downstream Passive Monitor is enabled,
the external partner clocks must be supplied as follows:

```text
DUT TX transmit bit clock  -> svt_port.rx_clk
DUT RX recovered bit clock -> svt_port.tx_clk
```

The `active_tx_transmit_clk` and `active_rx_recovered_clk` fields are outputs of
the SVT Active VIP intended to feed a Passive Monitor or another VIP.  They are
not the DUT PHY reference clock and are not driven by the scalar pad connector.

The DUT PHY reference clock remains a DUT-specific top-level connection.  The
scalar pad/data connectors do not provide Passive Monitor clock helpers; if a
Passive Monitor is enabled, its bit clocks must be wired explicitly at the DUT
top according to the SVT monitor interface contract.

## Validation

- A simulator-independent compile probe shall instantiate two 16-lane pad views,
  bind scalar pad names for both groups, and exercise x4, x8, and x16 connectors.
- The probe shall assert that the preprocessed/compiled design has no duplicate
  drivers and that lane slices are `[0 +: 4]`, `[0 +: 8]`, and `[0 +: 16]` for
  the single-pad cases.
- Existing SVT bridge contract checks and `git diff --check` must remain green.
