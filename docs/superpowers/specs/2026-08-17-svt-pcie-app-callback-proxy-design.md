# SVT PCIe Application-Callback Proxy Feasibility Design

**Date:** 2026-08-17

**Status:** Approved architecture, pending implementation plan and feasibility
probe

## 1. Purpose

This design replaces the failed Transaction Layer callback boundary in the
SVT PCIe Switch Proxy feasibility gate. The replacement must retain two real
Serial x4 Gen4 links and four normal R-2020.12 full Device Agents while using
only documented public SVT APIs to:

- capture and suppress switch-owned requests at each Proxy Target App;
- observe and return downstream Completions;
- reinject cloned TLPs through a different Proxy port; and
- prove that no Proxy Target App creates a duplicate response.

The design applies only to the Task 1 feasibility probe. The switch model and
production five-port integration remain blocked until every revised Task 1
gate passes.

## 2. Evidence Requiring the Revision

The original probe registered
`svt_pcie_tl_callback::pre_tlp_out_put` on the actual Proxy TL components in
`end_of_elaboration_phase`. Callback-pool diagnostics proved one enabled
callback on each expected component:

```text
uvm_test_top.ingress_proxy.port0.tl0
uvm_test_top.egress_proxy.port0.tl0
```

Both Serial links reached Gen4 x4 and the ingress TL and Target App received
the directed Memory Write. The TL callback, bridge capture, and reinjection
counters nevertheless remained zero. This experimentally disqualifies the
TL callback as the receive boundary for the R-2020.12 full Device Agent
active Target path used by this project.

The replacement uses two other documented public surfaces:

- `svt_pcie_target_app_callback::post_rx_tlp_get`, whose `drop` argument can
  discard a request after the Target App recognizes it; and
- `svt_pcie_agent::tl_mon.rx_tlp_observed_port`, which observes every complete
  received TLP but cannot suppress application processing.

## 3. Constraints

The revised probe must:

- keep all four participants as full Device Agents;
- keep the complete Serial, Physical, Data Link, and Transaction layers;
- use only public declarations documented in the installed R-2020.12 HTML;
- use `svt_pcie_agent::tlp_seqr` for raw egress reinjection;
- clone every vendor transaction before retaining it beyond the callback or
  analysis `write()` call;
- perform no blocking operation in a callback or analysis `write()` method;
- preserve the directed 10-bit Tag and all approved TLP fields;
- avoid private state, hierarchical `force` or `deposit`, and modifications
  to the Synopsys installation; and
- stop before Task 2 if any revised feasibility gate fails.

A custom HDL/RTL forwarding layer, Application Agent sidecar, and vendor
source modification are outside this design.

## 4. Architecture

### 4.1 Request capture and suppression

Each Proxy full Device Agent exposes `target[0]`. One
`svt_pcie_target_app_callback` is registered on each existing Target App in
`end_of_elaboration_phase`.

Its `post_rx_tlp_get` implementation accepts only the request classes needed
by the probe:

- Memory Write; and
- Configuration Read Type 0.

For a supported request it performs these nonblocking operations in order:

1. validate that the TLP and bridge handles are non-null;
2. clone the `svt_pcie_tlp`;
3. enqueue the clone with `mailbox::try_put`;
4. increment the request-capture counter; and
5. set `drop=1`.

The callback must not wait, start a sequence, call the switch, or retain the
vendor-owned transaction handle. A null TLP, clone failure, or failed
nonblocking enqueue emits `TL_PROXY_API_PROBE_BLOCKED` before a fatal.

### 4.2 Completion capture

Completions are received by the Requester/Driver side, not the Target App.
Each Proxy therefore connects a probe-owned analysis subscriber to the
public `pcie_agent.tl_mon.rx_tlp_observed_port`.

The subscriber ignores requests and captures only Completion and Completion
with Data TLPs. It clones each accepted TLP and performs a nonblocking enqueue
into the reverse mailbox. Filtering requests at this boundary prevents the
same request from being captured once by the monitor and once by the Target
callback.

The subscriber is observation-only. It does not modify the observed handle
and does not claim that the monitor analysis port suppresses any application
behavior.

### 4.3 Proxy Target response safety wall

The same Target App callback overrides `pre_tx_tlp_put`. Any TLP generated by
a Proxy Target App is counted and assigned `drop=1` before transmission. This
is a safety wall, not an alternate success path.

The final feasibility gate requires the Proxy Target transmit count to remain
zero. A nonzero count proves that `post_rx_tlp_get(drop=1)` did not fully
suppress local response generation and therefore blocks production use even
though the safety wall prevented a duplicate on the wire.

### 4.4 Bridge and raw reinjection

The bridge owns separate unbounded request and Completion mailboxes. Its
tasks perform blocking `get` outside callbacks, clone the queued object again,
create a fresh raw TLP sequence, and start it on the opposite Proxy's public
`pcie_agent.tlp_seqr`:

```text
source RC
  -> ingress Proxy Target callback
  -> request mailbox
  -> egress Proxy tlp_seqr
  -> sink EP

sink EP Completion
  -> egress Proxy TL monitor subscriber
  -> Completion mailbox
  -> ingress Proxy tlp_seqr
  -> source RC
```

The probe does not depend on `svt_pcie_tl_callback` for capture or drop.

## 5. Ownership and Exactly-Once Rules

The request and Completion paths have different, non-overlapping owners:

| TLP class | Capture owner | Suppression owner | Reinjection destination |
| --- | --- | --- | --- |
| MWr | Proxy Target callback | Target callback `drop` | opposite Proxy `tlp_seqr` |
| CfgRd0 | Proxy Target callback | Target callback `drop` | opposite Proxy `tlp_seqr` |
| CPL/CPLD | Proxy TL monitor subscriber | none | opposite Proxy `tlp_seqr` |

The TL monitor subscriber must never enqueue a request. The Target callback
must never enqueue a Completion. Every forwarding counter is incremented only
after the raw sequence returns successfully.

The raw request path may expose an R-2020.12 unexpected-Completion bookkeeping
limitation because it bypasses the Driver App transaction API. The probe must
not suppress, downgrade, or catch that diagnostic. Any resulting UVM warning,
error, or fatal fails the public-API feasibility gate.

## 6. Directed Feasibility Flow

The probe uses the existing reset and link-control sequence flow and requires
both real Serial pairs to reach Gen4 x4 L0. It then performs:

1. A one-DWORD Memory Write from the source RC with:
   - address `64'h0000_0000_8000_1040`;
   - `first_dw_be=4'hf`;
   - Tag `10'h12a`;
   - Requester ID `16'h0000`;
   - Traffic Class zero; and
   - payload DWORD `32'h4433_2211`.
2. A Type-0 Configuration Read of the sink Vendor/Device ID.
3. A bounded wait for the sink request observations and the source
   Completion.
4. Exact counter, field, duplicate-response, and UVM-report checks.

The sink and source observations remain independent public observation
callbacks or monitor subscribers. They do not participate in forwarding.

## 7. Pass and Stop Gates

The revised probe passes only when all of the following are true:

- two real Serial links reach Gen4 x4;
- Target callback registration is present and enabled on both Proxy
  `target[0]` instances;
- ingress request captures equal two;
- forward request reinjections equal two;
- reverse Completion captures equal one;
- reverse Completion reinjections equal one;
- the sink observes exactly one Memory Write with every directed field
  unchanged;
- the sink observes exactly one Type-0 Configuration Read;
- the source observes exactly one successful one-DWORD Completion;
- Proxy Target transmit count is zero;
- no unexpected or spurious Completion diagnostic occurs;
- `TL_PROXY_APP_CALLBACK_PROBE_PASS` appears exactly once;
- `TL_PROXY_API_PROBE_BLOCKED` does not appear; and
- final UVM warning, error, and fatal counts are `0/0/0`.

All link and packet waits remain bounded to 100 microseconds. A timeout prints
all capture, forward, observation, and Proxy Target transmit counters before
emitting the blocked marker and fatal.

If any gate fails, the implementation stops before Task 2 and reports the
specific public-API limitation. It must not weaken field checks, reduce the
Tag to eight bits, catch an unexpected-Completion report, or claim forwarding
from monitor observation alone.

## 8. Alternatives Considered

### 8.1 Target App `SET_PCT_DROP_REQ=100`

This public service can make the Target App drop all requests, but it is a
global percentage-based error-injection control. It has no per-class policy
and its documentation does not prove the absence of local side effects before
the drop. It remains a diagnostic fallback, not the production architecture.

### 8.2 Driver App transaction reconstruction

Reissuing captured requests through high-level Driver App sequences could
improve requester Completion bookkeeping. It would require class-specific
conversion and synthetic Completion reconstruction and would no longer prove
transparent raw TLP forwarding. It is not part of the revised Task 1 probe.

### 8.3 Custom HDL/RTL forwarding

An HDL/RTL forwarding layer materially expands scope and changes the selected
verification boundary. It is excluded unless the public Application-callback
probe fails and the user explicitly approves a new architecture.
